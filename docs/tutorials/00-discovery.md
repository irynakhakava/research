# Туториал · Фаза 0 · Discovery

Цель фазы: **зафиксировать границы продукта до написания пайплайна и индексов**.  
Без этого легко потратить недели на чанкинг и эмбеддинги, а потом выяснить, что ищем не те источники, не те типы вопросов и не умеем измерить «стало лучше».

> **Важно:** в этом проекте нет реальных данных и коннекторов.  
> Искать ответы будем только по статическому корпусу [`data/corpus/`](../../data/corpus/).  
> Каталог источников описывает демо-орг. NordLedger; URL — не для подключения.

В конце фазы у вас должны быть:

1. Каталог источников (метаданные) + статические тексты в `data/corpus/`  
2. Таксономия запросов  
3. NFR (latency, freshness как версия корпуса, ACL-модель)  
4. Definition of Done для MVP  
5. Первая версия gold-set (даже 30–50 примеров уже достаточно, чтобы стартовать)

---

## Зачем эта фаза нужна

RAG-система «ломается» не только на модели. Типичные провалы:

| Симптом в проде | Корневая причина, которую ловит Discovery |
|-----------------|-------------------------------------------|
| Ответ красивый, но не про нашу команду | Не описаны источники и ACL |
| Поиск «не находит очевидное» | Нет gold-set → нельзя измерить Recall |
| Пользователи спрашивают не how-to, а «где лежит X» | Не описана таксономия запросов |
| Индекс всегда устаревший | Не зафиксирован freshness SLA |
| Утечка чужой документации | Не продуманы фильтры доступа |

Discovery — это договорённость команды: *что* индексируем, *для кого*, *как поймём успех*.

## Шаг 1. Каталог источников

**Файл:** [`phase-0-discovery/sources.catalog.yaml`](../../phase-0-discovery/sources.catalog.yaml)

### Что сделать

1. Откройте `sources.catalog.yaml` (demo NordLedger уже заполнен).  
2. Для каждого логического корпуса в блоке `sources[]` проверьте owner, acl, priority.  
3. Убедитесь, что для `sample_doc_ids` существуют файлы в `data/corpus/<source_id>/`.  
4. Priority: `p0` — в MVP-индекс, `p1` — позже, `exclude` — не индексировать (даже если файлов нет).

### Почему так

Ингест без каталога превращается в «затянуть всё подряд». Потом:

- растёт шум в retrieval;
- сложно объяснить, почему ответ сослался на черновик;
- невозможно спланировать ACL-фильтры.

### Как заполнять (мини-правила)

- **Один source = один логический корпус** (например, «Confluence / Platform / runbooks», а не весь Confluence целиком).  
- **owner** обязателен — к кому эскалировать устаревшие страницы.  
- **acl** опишите хотя бы грубо: `public-to-company` / `team-only` / `need-to-know`.  
- Если источник «шумный» (митинги, личные заметки) — ставьте `exclude` или `p1` с комментарием.

### Критерий «шаг выполнен»

- Есть ≥1 источник со статусом `p0`.  
- У каждого `p0` заполнены: `system`, `location`, `owner`, `acl`, `language`, `update_cadence`.  
- В `notes` зафиксировано, что *не* берём в MVP.

## Шаг 2. Таксономия запросов

**Файл:** [`phase-0-discovery/query-taxonomy.md`](../../phase-0-discovery/query-taxonomy.md)

### Что сделать

1. Опирайтесь на демо-сценарии NordLedger (on-call, deploy, gateway) — реальных тикетов не будет.  
2. Разложите вопросы по типам из таксономии (или добавьте свой тип).  
3. Для каждого типа запишите 3–5 формулировок «как спрашивает человек», не идеальный поисковый запрос.

### Почему так

Разные типы запросов требуют разного retrieval:

| Тип | Что важно в поиске |
|-----|--------------------|
| how-to | пошаговые инструкции, runbooks |
| troubleshooting | симптомы, ошибки, «если видишь X» |
| where-is | точные названия сервисов, путей, owners |
| concept | определения, архитектурные overview |
| policy | правила, SLA, security guidelines |

Если 70% вопросов — troubleshooting, а вы оптимизируете чанкинг под длинные how-to, метрики offline будут хорошими, а пользователи — нет.

### Критерий «шаг выполнен»

- Заполнены примеры минимум для 3 типов запросов.  
- Отмечен **доминирующий** тип для MVP (тот, на котором сначала меряем качество).

## Шаг 3. Нефункциональные требования (NFR)

**Файл:** [`phase-0-discovery/nfr.md`](../../phase-0-discovery/nfr.md)

### Что сделать

1. Согласуйте с заинтересованными сторонами числа в таблице NFR (можно оставить разумные defaults и пометить `TBD`).  
2. Отдельно проговорите ACL: фильтруем *до* возврата чанков пользователю, не «после генерации».  
3. Зафиксируйте freshness для статики: индекс актуален после пересборки из `data/corpus`.

### Почему так

Без NFR нельзя выбрать стек:

- p95 latency 800 ms почти исключает тяжёлый LLM-rerank на каждый запрос;  
- freshness «раз в сутки» упрощает пайплайн, но убивает доверие к runbooks;  
- multi-tenant ACL меняет схему метаданных чанка с первого дня.

### Критерий «шаг выполнен»

- Заполнены целевые значения (или явные TBD с датой решения) для: latency, freshness, availability, ACL.  
- Есть формулировка «что делаем, если уверенности нет» (refuse / уточняющий вопрос).

## Шаг 4. Definition of Done MVP

**Файл:** [`phase-0-discovery/definition-of-done.md`](../../phase-0-discovery/definition-of-done.md)

### Что сделать

1. Прочитайте черновик DoD.  
2. Подставьте ваши пороги (Recall@10, доля ответов с корректными цитатами, p95).  
3. Явно перечислите *out of scope* MVP (чат с памятью, запись в Confluence, агенты с tools и т.д.).

### Почему так

DoD защищает от бесконечного «ещё один эксперимент».  
Фаза экспериментов (фаза 4) сравнивает варианты **относительно** этих порогов, а не абстрактного «нужно лучше».

### Критерий «шаг выполнен»

- DoD согласован хотя бы внутри команды разработки.  
- Есть 3–5 проверяемых критериев (не «удобный UX»).

## Шаг 5. Gold-set — измерительная линейка

**Каталог:** [`phase-0-discovery/gold-set/`](../../phase-0-discovery/gold-set/)

Gold-set — набор вопросов с эталоном: какие документы/фрагменты должны находиться, и (опционально) какой ответ считается правильным.

### Что сделать

1. Изучите схему: `schema.json`.  
2. Посмотрите примеры: `examples.jsonl`.  
3. Добавляйте свои кейсы в `dataset.jsonl` (один JSON-объект на строку).  
4. Прогоните валидатор:

```bash
python phase-0-discovery/gold-set/validate_gold_set.py
```

5. Цель на конец фазы 0: **≥ 30** валидных примеров; к фазе 4 желательно **50–150**.

### Как писать хороший кейс

**Плохо:**  
«Расскажи про деплой» — слишком широко, непонятно, что считать hit.

**Хорошо:**  
Вопрос: «Как откатить релиз сервиса payments в staging?»  
Релевантные документы: конкретный runbook + страница с командами rollback.  
Тип: `troubleshooting` или `how-to`.  
Заметки: частый вопрос дежурных.

Правила разметки:

- `relevant_doc_ids` — стабильные идентификаторы источников из каталога + путь/page id.  
- Можно помечать несколько релевантных документов; главный — в `primary_doc_id`.  
- Если правильный ответ «в документации этого нет» — используйте `expected_behavior: refuse` (такие кейсы тоже нужны).  
- Пишите вопрос языком пользователя, с опечатками/жаргоном — отдельными кейсами.

### Почему JSONL

- Удобно диффать в git.  
- Легко дописывать по одному кейсу.  
- Тот же файл потом читает eval-harness в фазах 2–4.

### Критерий «шаг выполнен»

- `validate_gold_set.py` завершается без ошибок.  
- В наборе есть кейсы ≥ 3 разных `query_type`.  
- Есть хотя бы 1 кейс с `expected_behavior: refuse`.

## Шаг 6. Короткий ADR (решение)

**Файл:** [`phase-0-discovery/adr-0001-mvp-scope.md`](../../phase-0-discovery/adr-0001-mvp-scope.md)

Зафиксируйте одной страницей:

- какие источники в MVP;  
- одно- или мульти-командный поиск;  
- язык(и);  
- будет ли генерация ответа уже в первом демо или сначала только `/search`.

Это не бюрократия: через месяц ADR отвечает на вопрос «почему мы так решили».

## Порядок работы на практике (1 неделя)

| День | Действие | Артефакт |
|------|----------|----------|
| 1 | Интервью с 2–3 владельцами документации / дежурными | черновик каталога + таксономия |
| 2 | Заполнить `sources.catalog.yaml`, вычеркнуть шум | каталог p0/p1 |
| 3 | Согласовать NFR и DoD (даже async в чате) | `nfr.md`, `definition-of-done.md` |
| 4–5 | Набрать gold-set (по 10–15 кейсов/день) | `dataset.jsonl` |
| 5 | Прогнать валидатор, дописать ADR | зелёный validate + ADR |

## Частые ошибки

1. **Gold-set из идеальных вопросов.** Потом модель хорошо работает на eval и плохо в Slack.  
2. **Один гигантский source «вся вики».** Неуправляемые ACL и шум.  
3. **DoD без чисел.** Невозможно остановить эксперименты.  
4. **Игнор refuse-кейсов.** Система всегда что-то выдумывает.  
5. **Откладывание ACL «на потом».** Потом приходится перекладывать метаданные чанков.

## Где лежит контент для поиска

Статические тексты документов (то, по чему ищем ответы):

- каталог: [`data/corpus/`](../../data/corpus/)
- индекс id→файл: [`data/corpus/manifest.json`](../../data/corpus/manifest.json)

Пример: вопрос про rollback → документ  
`data/corpus/platform-confluence-runbooks/plat-runbook-payments-rollback.md`.

## Что делать прямо сейчас

1. Откройте `phase-0-discovery/sources.catalog.yaml` (demo NordLedger уже заполнен).  
2. Добавьте вопросы в `phase-0-discovery/gold-set/dataset.jsonl` и при необходимости новый `.md` в `data/corpus/`.  
3. Выполните:

```bash
python phase-0-discovery/gold-set/validate_gold_set.py
python data/corpus/verify_corpus.py
```

Если валидатор ругается — он подскажет, какое поле поправить. Это нормальный цикл фазы 0.
